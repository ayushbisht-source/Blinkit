1 How the workflow gathers and analyses data

Collect wide, then spend model budget only on the documents that survive a cheap filter.

Two numbers, and which one every figure below refers to

The corpus was widened late — from 5 apps to 11, adding broad marketplaces and category specialists (beauty, pharma, meat) whose reviews discuss the specific categories this project is about. That collection succeeded: 5,898 documents are committed in data/interim/documents.jsonl and reproducible from .github/workflows/collect-appstores.yml.

The 2,526 newly collected documents have not been through the gate or extraction. Every theme, insight and validation figure on this page therefore describes the original 3,372-document run: 971 judged relevant, 937 extracted, 25 themes. Enrichment is resumable, so processing the remainder is a re-run rather than a rebuild — it simply did not fit before submission. Reporting the larger number as if it had been analysed would be the easiest thing on this page to get wrong, so it is separated explicitly instead.

What is not in the corpus, stated up front

A Reddit collector is implemented (engine/collectors/reddit.py) and contributed zero documents, and the reason is measured rather than assumed: a collection run from CI returned HTTP 403 on 117 of 117 requests, with Reddit's HTML block page as the body. Reddit refuses unauthenticated reads from datacenter IP ranges. An authenticated path against oauth.reddit.com is implemented and needs only credentials. So the corpus is app-store review text only — and this is not a footnote: a review corpus contains only people who completed a transaction, so every barrier that stops someone before they buy is invisible to it by construction. Section 4 returns to what that cost, and the interviews in Part 2 exist largely to cover it.

Normalisation, before any model sees a document

  • PII scrubbing — emails and phone numbers stripped; usernames hashed with a salt at ingestion, so raw handles are never written to disk.
  • Near-duplicate removal via MinHash — app-store corpora are full of near-identical one-liners that would otherwise inflate every theme's prevalence.
  • Hinglish detection, so code-mixed reviews are kept rather than discarded as malformed English.

A two-stage model pass, not one

Running structured extraction over 3,372 documents would spend most of the budget on reviews about delivery times. So a cheap relevance gate runs first and only survivors reach extraction.

StageInOutWhat it does
Relevance gate3,372971 (28.8%) Cheap model judges whether the text says anything about what someone chooses to buy
Extraction971937 (96.5%) Structured output against engine/schema.py — barriers, habit drivers, information gaps, segment signals, and one verbatim pain statement

Rejected as noise: delivery 941 · support 550 · contentless 527 · technical 252 · unrelated 132. The gate removing ~71% of the corpus is the design, not a loss — most app-store reviews are about how fast the order arrived, which says nothing about category choice.

The gate has a measured error rate, and it is reported rather than tuned away

An interviewee described building their basket around a free-delivery threshold — a genuine constraint on what gets bought, expressed as a fee complaint. Re-checking the corpus, 133 documents use that language and the gate discarded 64 of them as delivery or support noise (check_basket_economics.py). The filter's premise is right most of the time and wrong in a specific, identifiable way. That is part of what the engine's output means, so it is documented instead of quietly retuned.

Two rules that constrain the whole pipeline

  • The schema is the single source of truth. Every enum in engine/schema.py traces to one of the brief's eight research questions, so coverage of the brief is checkable rather than asserted.
  • Numbers never come from a model. Prevalence, counts, source spread and segment skew are computed from data and carried through untouched. The model sees labels and quotes only — it cannot inflate a statistic it is never shown.

2 How themes are identified

Deterministic clustering over the extracted pain statements — no model involved at this stage at all.

pain statements  →  TF-IDF  →  LSA (TruncatedSVD)  →  agglomerative clustering  →  centroid merge  →  25 themes

Clustering runs on the extracted pain statements, not raw reviews, so the grouping is over structured claims rather than over whatever vocabulary a reviewer happened to use. Character-level n-grams (char_wb, 3–5) handle the paraphrase and spelling variation that word n-grams miss in code-mixed text.

The merge threshold was calibrated, and silhouette could not do it

The obvious approach — pick the number of clusters by silhouette score — does not work here. Silhouette is monotone in k on both the sparse TF-IDF and the dense LSA representation, so it always prefers more clusters and can never select. Adjusted Mutual Information and V-measure are dominated by completeness, which is maximised by the degenerate one-cluster solution.

What was used instead: a reproducible sweep against a synthetic corpus with planted themes, selecting on homogeneity, which plateaus at 0.35 (calibrate_merge.py). Purity is flat across 0.25–0.40 and cannot discriminate either. The chosen value is DEFAULT_MERGE_AT = 0.35.

The failure this was written to catch

At the original threshold of 0.12 the clustering collapsed to a single theme covering 100% of documents — and reported success. A one-theme result is technically a valid clustering and every downstream stage accepted it. Two guards now exist: assert_not_degenerate(), and a MAX_THEME_SHARE of 0.60 so no theme may swallow the corpus. Recalibration to 0.35 produced the 25 interpretable themes used throughout.

THM-05 is the theme that proved a prediction

An interviewee's account of basket-shaping around a delivery threshold predicted that this behaviour would exist in the corpus but be miscoded. It clustered into a theme of its own — 34 statements, 5.4% — which the pipeline then labelled price_risk, meaning "unsure whether the price is fair". Its quotes are people re-planning a basket around a threshold that moved: "Before it serves free delivery on 100₹, And now 400₹." These users know exactly what the fee is. The theme is real; no value in the schema fits it. The engine collected the signal at scale and has nowhere to store it.

3 How insights are generated

Themes go to a model for interpretation; every number stays out of its reach.

Each theme is passed to the model with its labels and its verbatim quotes, and the model returns a mechanism, a confidence, and the research questions the theme answers. Batches of three, so a single failure costs three themes rather than twenty-five.

Three constraints on what a model is allowed to do

  • It never sees a statistic. Prevalence and counts are computed before synthesis and re-attached after it, so a number in the output is arithmetic, not generation.
  • Contradicting evidence is computed, never requested. Asking a model for evidence against its own conclusion reliably returns nothing useful. Instead the code counts documents inside each theme whose labels disagree with that theme's dominant barrier.
  • Placeholders cannot ship. If a client is configured and nothing was synthesised, the run exits non-zero rather than writing 25 empty insights and reporting success — which is exactly what an earlier version did.

Confidence is self-scored, and low scores are kept

Median confidence across the 25 insights is 0.85. THM-03 scored itself 0.35 and declined to assert a mechanism its evidence did not support. That row was kept rather than dropped or rewritten — a synthesis step that never produces a low-confidence output is not being honest about anything.

Provider independence

The client is provider-agnostic (Anthropic → Gemini → Groq) with account-level failover, because a single free-tier quota should not be able to end a run. The final synthesis ran on Gemini; the cross-check in section 4 re-ran the entire step on a different model family.

4 How the quality of the insights was validated

Six checks. Four pass, two report NOT RUN — and the two that abstain are the more informative half.

Every figure below is read from data/processed/validation.json, the artifact the pipeline actually wrote. The checks need no API key, so anyone can re-run them: python -m engine.validation.checks

CheckResultWhat it measured
Quote groundingPASS 924 extracted quotes checked character-for-character against source text. 917 exact, 3 whitespace-normalised, 4 fabricated (0.43%). Of the 125 quotes that reach a theme, 0 are unverifiable — clustering filters them out first.
Theme saturationPASS Across 937 documents, 15 distinct labels. 95.3% of them were found by the halfway point, and the final decile yields 0.003 new labels per document. Collecting more of the same source would not have found more kinds of thing.
Hold-out generalisationPASS Genuinely out-of-sample: vectoriser, LSA and clustering re-fit on 505 training statements only, then 126 unseen statements assigned to nearest centroid. Hold-out fit 0.460 vs training's own 0.462 — unseen data fits essentially as well as seen data — against a size-matched permutation null of 0.341, z = 11.42.
Relevance gate auditPASS 40 of the 2,402 rejected documents sampled and re-read for false negatives. 0 found in the sample. Note the ceiling: 40 of 2,402 can bound a large error rate, not a small one — and the basket-economics gap in section 1 was found by interview, not by this audit.
Source spreadNOT RUN The corpus is 95.1% a single source (600 Play Store vs 31 App Store among themed documents). 11 of 25 themes are single-source, but 8.6 would be by chance at that mix — so the check cannot separate a platform artifact from a finding, and says so instead of returning a green tick.
Human agreement (Cohen's κ)NOT RUN Requires a hand-labelled gold set (data/gold/labels.jsonl) that does not exist. Reported as absent rather than approximated with a model-labelled substitute, which would measure agreement between a model and itself.

Why two checks report NOT RUN instead of PASS

Earlier versions of this suite printed PASS over zero observations. The grounding check ran against themes that were never passed in, so "no unverifiable quotes used" was measured over an empty set. The hold-out check compared training data to itself. Both were green, and both were meaningless.

A green line standing for no evidence is worse than an honest gap, because it is the failure mode that survives review. Four checks pass, two abstain, and the report says which is which.

The hold-out null was designed so the check could fail

The obvious floor — similarity to a randomly chosen centroid — is far too weak, because taking the maximum over 25 centroids is biased upward regardless of what those centroids contain. Measured against that floor, word-salad statements built from the real corpus vocabulary scored 0.71 and passed, despite containing no structure at all.

The null in use keeps the geometry and destroys only the grouping: the same training points are assigned to clusters of the same sizes at random. Verified by mutation during development — real statements scored z = +17.4, and the same statements with every pain statement replaced by random corpus vocabulary scored z = −2.6, below the null and correctly failing. (Those two figures come from the mutation test in checks.py, not from the stored run above, which scored 11.42 on its own data.)

Cross-checked against a second model family

Everything else in the engine is counted or verified; the mechanism prose is not. So synthesis was re-run end to end on Llama 3.3 70B and compared against the Gemini output across all 25 themes.

5 Run it yourself

Every stage is reproducible; the validation stage needs no key.

pip install -r requirements.txt
cp .env.example .env                     # set AUTHOR_HASH_SALT; add an API key for enrichment

python -m engine.collect --per-app 1000  # ~3.4k documents
python -m engine.pipeline.enrich         # gate + extract   (needs an API key)
python -m engine.pipeline.cluster        # themes           (deterministic, no key)
python -m engine.pipeline.synthesize     # insights         (needs an API key)
python -m engine.validation.checks       # validation       (no key needed)

Enrichment is resumable — completed document ids are skipped, so an interrupted run costs a retry rather than the run. Everything also runs on GitHub Actions (.github/workflows/analyse.yml), which is how it was actually executed: the development sandbox is network-restricted from the review endpoints.
